# Content QA

Review the actual rendered draft against its brief and claim ledger. Return
`pass`, `revise` or `blocked`, with exact passages, evidence and actionable fixes.
QA readiness, successful deployment and proven growth are different states.

| Check | Acceptance |
| --- | --- |
| Reader and intent | The page answers the named audience's question, supplies a useful next step and adds something beyond the existing ranking pages. |
| Readability | Use familiar words, explain necessary jargon and shorten tangled sentences. Aim around grade 7 for a general audience; treat readability scores as a diagnostic, not a reason to distort technical meaning. |
| Writing quality | Remove generic openings, filler, repetitive formulas, keyword stuffing and unsupported superlatives. Follow the owner's voice; punctuation rules alone cannot certify human-quality prose. Use `humanizer` for a dedicated AI-prose edit when useful. |
| Claims | Open each material source. Check dates, pricing, features, comparisons and numbers. Distinguish documented behavior from personally tested behavior. No invented quotes, customers, benchmarks or experience. Missing evidence blocks the claim or requires removing it. |
| SEO and structure | Useful title/description, clear main heading, correct indexability/canonical, descriptive links, genuine intent coverage and structured data supported by visible content. Check likely cannibalization with query/page evidence rather than similar titles alone. |
| Images | Relevant screenshot or illustration, permission/source where needed, accurate labels, alt text, correct sizing and acceptable load behavior. A decorative stock image is not product proof. Never expose private dashboards or personal data. |
| Internal links | Follow the actual links to valid canonical destinations. Check the surrounding sentence and anchor, not just link presence. |
| CTA and measurement | The CTA fits the reader's stage, makes a truthful promise, reaches the right destination and can be followed. Verify existing conversion instrumentation where access permits; otherwise mark it unverified. Do not submit a real purchase/signup merely to test tracking without scope. |
| Rendered page | Review phone, tablet and desktop previews for headings, tables, images, links, CTA and overflow. Use existing design direction. A build pass does not prove the layout works. |

The QA result identifies the draft revision, reviewed scope, unresolved issues,
source timestamps and checks actually performed. `Pass` needs no unresolved
material defect; blocked access cannot silently become a pass. A writer fixes
the defects and resubmits the changed portions for review. After two unsuccessful
revision rounds, record what evidence or decision is missing and stop publication.

## Outcome review

Retain the pre-change revision and baseline. Pick a check date based on the
available data lag, traffic and the change; do not impose a universal waiting
period or change content repeatedly before enough new evidence exists.

For each URL record search impressions/clicks/CTR and relevant queries when
available, attributed visits, defined conversion events and rate denominator,
and separately any AI mention/citation observations. Preserve unknowns, complete
periods, bot exclusions, concurrent changes and seasonal effects. A click, page
view, recorded session or editor's acceptance is not a paid customer.

Use the result to improve the next brief. Choose an exact content/technical/CTA
change only when evidence supports it; a well-performing article can stay as is.
